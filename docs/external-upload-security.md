# 글쓰기·어드민 전용 이미지 업로드 보안 정책

## 결론

**우리 서비스의 글쓰기와 어드민 페이지에서 필요한 업로드만 지원합니다.** 외부 사이트,
제3자 클라이언트, 비인증 사용자에게 제공하는 업로드 API는 지원하지 않습니다.
우리 화면의 브라우저도 이미지 서버를 직접 호출하지 않고 권한을 검증하는 자사 백엔드를 거칩니다.
현재 API key는 업로드와 전체 자산 삭제를 허용하므로 브라우저/배포된 앱에 넣지 않습니다.
CORS, Origin, Referer만으로는 접근 권한을 보장할 수 없습니다.

이 PR은 이 정책을 문서에 반영하며 외부 업로드 경로, CORS, 직접 업로드 티켓을 추가하지 않습니다.
실제 사용자 권한 검증은 자사 백엔드, 외부 네트워크 차단은 Nginx/방화벽에서 별도 적용·검증해야 합니다.
현재 이미지 서비스의 API key 검사만으로 이 네트워크 차단까지 완료되었다고 판단하면 안 됩니다.

## 허용하는 요청 흐름

```text
글쓰기 화면 -> 로그인·글쓰기 권한 확인 -> 자사 백엔드 --내부 통신--> 업로드 서비스
어드민 화면 -> 로그인·관리자 권한 확인 -> 자사 백엔드 --내부 통신--> 업로드 서비스
외부 사이트·제3자·비인증 요청 -----------------------> 거부
```

백엔드는 화면 표시 여부가 아니라 매 요청의 로그인·글쓰기/관리자 권한을 서버에서 검사합니다.
쿠키 인증이면 CSRF도 방어하고 업로드 목적·크기·개수·사용자별 저장량을 제한합니다. 현재 API key는
서버 secret으로만 관리하고 주기적으로 교체합니다. 서로 다른 키를 등록해도 현재 코드는 권한 범위를
구분하지 않으므로 이를 '업로드 전용 키'라고 부르면 안 됩니다. 이미지 서버의 `/upload`는
공개 Nginx에서 proxy하지 않고 거부합니다. API key가 있어도 외부망에서 이 경로로 들어올 수 없게 합니다.
서버 간 reverse proxy가 필요하면 별도의 내부 listener와 자사 백엔드 allowlist를 사용합니다.
`/assets/*`와 `/healthz`도 내부 관리망으로 제한하고 원본 API 포트 접근을 방화벽으로 제한합니다.

사용자 백엔드는 전달받은 URL 문자열만 믿고 프로필에 연결하지 않습니다. 자신이 업로드한 결과의
자산 식별자/소유자/공개 URL prefix를 검사하고 저장합니다. 같은 내용은 해시로 공유될 수 있으므로
프로필에서 해제했다고 공통 원본을 즉시 DELETE하면 다른 사용자 이미지를 지울 수 있습니다.
서비스에 소유권/참조 수 모델을 넣기 전에는 사용자 직접 삭제 대신 백엔드 참조 해제와 별도 정리를 권장합니다.

## 지원하지 않는 방식

- 누구나 사용할 수 있는 공개 `/upload` API와 제3자용 업로드 키 발급.
- 브라우저/배포된 앱에 정적인 이미지 서비스 키를 포함하는 방식.
- 자사 백엔드 권한 검사를 우회하는 직접 업로드와 presigned URL·단기 티켓 발급 기능.

글쓰기·어드민 업로드 지원은 이 기능들을 도입한다는 뜻이 아닙니다. 업로드만 된 미연결 파일의
정리와 삭제 권한도 자사 백엔드가 관리해야 하며, 원본 삭제 전 공유 참조를 확인합니다.

## 현재 방어와 추가 과제

| 항목 | 현재 코드 | 글쓰기·어드민 연동 시 과제 |
| --- | --- | --- |
| 쓰기 인증 | API key/Bearer 필요 | 장기 키 서버 보관, 키별 범위/소유권은 미구현 |
| 파일 검증 | file/sips/Pillow, MIME allowlist, 크기·픽셀 제한 | 디코더 최신 보안 패치, 불필요 포맷 축소 검토 |
| 경로 | 내용 SHA-256, 원자적 저장 | 해시는 권한/비공개 보장이 아님 |
| 자원 제한 | worker 수, HTTP/이미지/DB timeout | Nginx IP 제한 + 앱 사용자 쿼터 + 총 디스크 한도/알림 |
| 원본 개인정보 | 업로드 원본 보존 | EXIF GPS/촬영 정보 제거 정책, 동의/보관기간 결정 |
| 악성/불법 콘텐츠 | 이미지 형식 확인 | 필요 시 격리·검사·신고·차단, 검사 전 Nginx 노출 금지 |
| 사용자 삭제 | 전역 키로 자산 삭제 | 소유권/공유 참조/감사로그와 재시도 설계 |
| 캐시 | immutable 공개 URL | 민감 이미지 금지, 삭제 즉시 회수 보장 안 됨 |

MIME 판별과 이미지 파싱만으로 원본 안의 모든 악성 데이터가 제거되지는 않습니다. 공개 프로필
이미지는 서버 재인코딩된 제한 포맷을 배포하는 정책도 검토해야 합니다. 다만 원본 해시/URL 계약이
달라질 수 있어 별도 변경으로 진행합니다. 현재 원본에 자동 EXIF 제거가 있다고 가정하지 마세요.

현재 Nginx의 `1년 immutable` URL은 누구나 URL을 알면 읽을 수 있고 파일 삭제 후에도 클라이언트에
남을 수 있습니다. 사적인 사용자 사진/문서용이면 지금의 공개 정적 경로 대신 인증된 전달 및 짧은
캐시 정책이 필요합니다. 사용자 이미지가 공개 프로필 사진인지부터 구분해야 합니다.

## Nginx 전달 체크리스트

- 글쓰기/어드민의 사용자 백엔드 연결은 HTTPS로 보호하고 백엔드→이미지 서버는 사설망/VPN을 사용합니다.
- 공개 이미지 Nginx에서 `/upload`와 `/upload/`를 포함한 API 경로를 차단하고 원본 API 포트도 외부에 열지 않습니다.
- 내부 proxy가 필요한 경우 자사 백엔드만 allowlist로 허용합니다. 키를 로그/URL query에 남기지 않습니다.
- `client_max_body_size`는 애플리케이션의 파일 한도보다 multipart 오버헤드만큼 여유 있게 맞춥니다.
- 요청률/동시 연결/본문 수신·upstream timeout을 설정하고 임시 업로드 디스크도 감시합니다.
- `/upload`, `/assets`, `/healthz`에는 정적 이미지 캐시 규칙이나 `proxy_cache`를 적용하지 않습니다.
- 이미지 정적 경로는 실행 처리하지 않고 정확한 Content-Type, `X-Content-Type-Options: nosniff`를 설정합니다.
- dotfile/임시 파일/디렉터리 목록은 거부하고 서비스 코드·`.env`·DB 파일은 절대로 alias하지 않습니다.
- `X-Image-Release`/`X-Image-Pid`와 health 경로는 내부 진단용이며 공개하지 않습니다.

연동 전 검증: 글쓰기 권한·관리자 권한별 정상 업로드, 비로그인·권한 없는 요청 거절, CSRF 방어,
공개 이미지 도메인의 업로드 거부(키 유무와 무관), 원본 API 포트 외부 차단, 내부 정상 키/잘못된 키 검사,
비허용 형식/초과 크기 거절, 속도 제한, 공개 DELETE/메타데이터 차단, SMB 회복, 로그 비밀값 미노출.
이번 PR에서는 공개 Nginx 설정을 바꾸지 않았으므로 이 E2E 항목들은 아직 검증 완료가 아닙니다.
