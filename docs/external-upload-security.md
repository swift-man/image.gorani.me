# 외부 업로드 보안 검토

## 결론

**신뢰하는 백엔드에서 HTTPS로 업로드하는 방식은 조건부로 가능**합니다. 브라우저/배포된 Swift
앱에 현재의 공용 API key를 넣어 직접 업로드하도록 공개하면 안 됩니다. 이 키는 업로드뿐 아니라
모든 자산 삭제도 허용하며 사용자별 소유권이 없습니다. CORS는 인증이나 키 보호 장치가 아닙니다.

외부 업로드 공개와 관련해서는 현재 PR에서 검토 문서만 추가합니다. Nginx 공개 `/upload`, CORS, 단기 토큰, 사용자별 삭제 권한은
새로 구현하거나 활성화하지 않습니다. 외부 업로드 경로는 Nginx 프로젝트에서 별도 적용/검증합니다.

## 권장 1단계: 사용자 백엔드 경유

```text
브라우저/Swift 앱 -> 로그인된 사용자 백엔드 -> HTTPS Nginx -> 업로드 서비스
                          | 사용자 권한/쿼터               | 서버 전용 API key
                          +<- 응답의 image URL/asset ID <---+
```

백엔드가 사용자를 인증하고 업로드 목적·크기·개수·사용자별 저장량을 제한합니다. 현재 API key는
서버 secret으로만 관리하고 주기적으로 교체합니다. 서로 다른 키를 등록해도 현재 코드는 권한 범위를
구분하지 않으므로 이를 '업로드 전용 키'라고 부르면 안 됩니다. Nginx에서 외부 접근은 정확히
`POST /upload`만 허용하고 `/assets/*` 삭제·메타데이터와 `/healthz`는 내부 관리망으로 제한합니다.
백엔드 IP 제한 또는 mTLS를 추가하면 유출 키의 위험을 줄일 수 있습니다.

사용자 백엔드는 전달받은 URL 문자열만 믿고 프로필에 연결하지 않습니다. 자신이 업로드한 결과의
자산 식별자/소유자/공개 URL prefix를 검사하고 저장합니다. 같은 내용은 해시로 공유될 수 있으므로
프로필에서 해제했다고 공통 원본을 즉시 DELETE하면 다른 사용자 이미지를 지울 수 있습니다.
서비스에 소유권/참조 수 모델을 넣기 전에는 사용자 직접 삭제 대신 백엔드 참조 해제와 별도 정리를 권장합니다.

## 브라우저가 먼저 업로드하려면

백엔드 트래픽을 피하려면 아래 기능을 먼저 개발해야 합니다. **현재 API로 가능한 기능이 아닙니다.**

1. 로그인 백엔드가 수분 이내 만료하는 업로드 전용 티켓을 발행합니다. 사용자, 목적, 최대 바이트,
   허용 MIME, 고정 썸네일 정책, `aud`, `exp`, 일회용 `jti`를 서명에 묶습니다.
2. 업로드 서비스가 서명/만료/범위를 검사하고 DB의 고유 키로 `jti`를 원자적으로 소비합니다.
   동시 재사용을 막고 네트워크 오류 후 재시도는 동일 결과를 돌려주는 별도 상태로 설계합니다.
3. 브라우저는 그 티켓으로만 업로드합니다. 장기 관리자 키나 발급용 서명키를 받지 않습니다.
   정확한 Origin allowlist와 필요한 OPTIONS/헤더만 허용합니다. 쿠키 인증이면 CSRF 방어도 필요합니다.
4. 백엔드는 업로드 완료 상태와 소유권을 확인하고 자산을 사용자 프로필에 연결합니다. 업로드만 된
   미연결 파일에는 만료/정리 정책을 둡니다. 다른 사용자의 URL을 제출해 연결하는 것을 막습니다.
5. 삭제도 자산 소유권/공유 참조를 검사하는 별도 사용자 API로 제공합니다. 티켓에 삭제 권한은 없습니다.

## 현재 방어와 추가 과제

| 항목 | 현재 코드 | 외부 공개 전 과제 |
| --- | --- | --- |
| 쓰기 인증 | API key/Bearer 필요 | 장기 키 서버 보관, 키별 범위/소유권은 미구현 |
| 파일 검증 | file/sips/Pillow, MIME allowlist, 크기·픽셀 제한 | 디코더 최신 보안 패치, 불필요 포맷 축소 검토 |
| 경로 | 내용 SHA-256, 원자적 저장 | 해시는 권한/비공개 보장이 아님 |
| 자원 제한 | worker 수, HTTP/이미지/DB timeout | Nginx IP 제한 + 앱 사용자 쿼터 + 총 디스크 한도/알림 |
| 원본 개인정보 | 업로드 원본 보존 | EXIF GPS/촬영 정보 제거 정책, 동의/보관기간 결정 |
| 악성/불법 콘텐츠 | 이미지 형식 확인 | 필요 시 격리·검사·신고·차단, 검사 전 Nginx 노출 금지 |
| 사용자 삭제 | 전역 키로 자산 삭제 | 소유권/공유 참조/감사로그와 재시도 설계 |
| 캐시 | immutable 공개 URL | 민감 이미지 금지, 삭제 즉시 회수 보장 안 됨 |

MIME 판별과 이미지 파싱만으로 원본 안의 모든 악성 데이터가 제거되지는 않습니다. 공개 프로필
이미지는 서버 재인코딩된 제한 포맷을 배포하는 정책도 검토해야 합니다. 다만 원본 해시/URL 계약이
달라질 수 있어 별도 변경으로 진행합니다. 현재 원본에 자동 EXIF 제거가 있다고 가정하지 마세요.

현재 Nginx의 `1년 immutable` URL은 누구나 URL을 알면 읽을 수 있고 파일 삭제 후에도 클라이언트에
남을 수 있습니다. 사적인 사용자 사진/문서용이면 지금의 공개 정적 경로 대신 인증된 전달 및 짧은
캐시 정책이 필요합니다. 사용자 이미지가 공개 프로필 사진인지부터 구분해야 합니다.

## Nginx 전달 체크리스트

- HTTPS만 허용하고 Nginx→Mac 구간은 사설망/VPN, 필요하면 TLS로 보호합니다.
- 정확한 `/upload`만 proxy하고 POST 외 방법은 거절합니다. 사용자 키를 로그/URL query에 남기지 않습니다.
- `client_max_body_size`는 애플리케이션의 파일 한도보다 multipart 오버헤드만큼 여유 있게 맞춥니다.
- 요청률/동시 연결/본문 수신·upstream timeout을 설정하고 임시 업로드 디스크도 감시합니다.
- `/upload`, `/assets`, `/healthz`에는 정적 이미지 캐시 규칙이나 `proxy_cache`를 적용하지 않습니다.
- 이미지 정적 경로는 실행 처리하지 않고 정확한 Content-Type, `X-Content-Type-Options: nosniff`를 설정합니다.
- dotfile/임시 파일/디렉터리 목록은 거부하고 서비스 코드·`.env`·DB 파일은 절대로 alias하지 않습니다.
- `X-Image-Release`/`X-Image-Pid`는 내부 진단용입니다. health 경로를 공개할 경우 이 헤더를 제거합니다.

승인 전 검증: 정상 키 업로드/잘못된 키 401, 비허용 형식/초과 크기 거절, 속도 제한, 공개 DELETE 차단,
비인증 메타데이터 접근 차단, SMB 단절 후 회복, 로그 비밀값 미노출, 원본/썸네일 정적 URL 확인.
이번 PR에서는 공개 Nginx 설정을 바꾸지 않았으므로 이 E2E 항목들은 아직 검증 완료가 아닙니다.
