# 배포 후속 개선과 0.4.0 전환

## 적용 범위와 Python 전환

Python 3.11 이상이 필요합니다. Python 3.9에서 설치되는 Pillow 11.3 계열을 계속 고정하는 대신
Pillow 13.0.0과 python-multipart 0.0.32로 전환합니다. 기존 사용자 환경의 Python과 `.venv`를
이 PR이나 배포기가 자동 교체하지 않습니다. 운영 적용 전에 아래 순서를 따릅니다.

1. 기존 main, `.env`, 서비스 plist, 배포 설정을 비공개 위치에 백업합니다.
2. Python 3.11 또는 3.12의 별도 가상환경에서 lock 설치, 프로젝트 빌드, `pip check`, 전체 시험을 실행합니다.
3. 유지보수 시간에 runner 배포를 비활성화하고 원격 배포가 끝난 것을 확인한 뒤 updater/서비스를 중지합니다.
4. `auto-deployment.md`의 수동 업그레이드 절차에 따라 기존 배포 설정을 복원하고 운영 checkout/가상환경을 전환합니다.
5. 새 Python으로 서비스와 배포기를 설치하고 SMB/DB/health, 글쓰기·어드민 업로드를 확인한 뒤 자동 배포를 켭니다.

기존 배포기는 자기 코드 변경을 거부하므로 이번 릴리스는 자동 갱신 대상이 아닙니다.
실패하면 백업한 checkout/가상환경/plist로 복원합니다. 운영 `.env`, 이미지 파일, DB는 교체 대상이 아닙니다.

## 의존성 lock

CI와 배포는 동일한 `requirements-deploy.txt`를 사용합니다. 런타임뿐 아니라 setuptools/wheel 및
전이 의존성을 고정합니다. 해시 불일치와 지원 wheel 부재는 설치 실패로 처리하고 기존 release를 유지합니다.
Python/OS/pip 자체와 외부 `sips`, `file`, PostgreSQL은 lock 범위 밖입니다. 바이트 단위로 동일한
애플리케이션 wheel 재생성을 보장한다는 의미는 아닙니다.

버전 갱신 시 `pyproject.toml`과 `requirements-deploy.in`을 함께 수정하고 별도 도구 환경에서:

```sh
python3.11 -m venv /tmp/image-lock-tools
/tmp/image-lock-tools/bin/python -m pip install pip-tools==7.6.2
/tmp/image-lock-tools/bin/pip-compile --generate-hashes --allow-unsafe --strip-extras \
  --no-emit-index-url --no-emit-trusted-host --output-file requirements-deploy.txt requirements-deploy.in
```

생성된 diff의 버전/해시를 검토하고 3.11/3.12에서 새 가상환경 설치 및 전체 시험을 통과시킵니다.
해시는 다운로드 무결성 검증이지 취약점 부재의 보장이 아닙니다. 보안 공지는 주기적으로 확인해야 합니다.

## SSH 키 최소 권한

배포 설치 시 안정 디렉터리에 `ssh-entry.sh`를 복사합니다. 기존 runner의 아래 명령만 허용하고
셸, SCP/SFTP, 추가 인자/명령은 거부합니다. 입력을 `eval`하지 않습니다.

```sh
exec "$HOME/Library/Application Support/gorani-image-upload/deploy/sync.sh"
```

운영자가 별도 전용 키를 준비하고 authorized_keys에 다음 형식으로 직접 등록합니다.
경로와 공개키는 예시를 실제 값으로 바꾸되 저장소에 커밋하지 않습니다.

```text
restrict,command="/bin/sh '/ABSOLUTE/DEPLOY/DIRECTORY/ssh-entry.sh'" ssh-ed25519 PUBLIC_KEY
```

`restrict`는 포워딩/PTY 등의 기능을 제한합니다. 키가 쓰이는 다른 자동화가 있으면 기존 키를
그대로 제한하지 말고 전용 키로 분리하세요. 위 원격 명령 문자열은 기존 runner와의 고정 요청
식별자이므로 `--root`로 설치해도 변경하지 않습니다. 실행 대상은 authorized_keys에 절대 경로로
등록한 `ssh-entry.sh`와 같은 디렉터리의 `sync.sh`입니다. 기본 경로에 다른 설치가 있어도 호출하지
않습니다. 진입점은 다른 위치의 심볼릭 링크가 아닌 설치된 파일 자체를 등록하세요.
키 파일 권한 0600, 신뢰한 known_hosts, 내부망 접근 제한을 유지합니다. 강제 명령만으로
runner 장비 침해나 동일 운영 사용자 권한을 격리할 수는 없습니다.

## 중단 검증: 완료된 것과 남은 것

자동 시험은 임시 디렉터리와 실제 자식 프로세스를 사용하여 전환 후 SIGKILL로 끊고, 다음
recover가 이전 포인터로 복원하며 실패 SHA를 차단하는지 검증합니다. 네이티브 launchd/SSH/SMB를
이 시험에서 호출하지 않습니다. 가짜 시계는 sleep에 의해서만 전진하므로 시간 조회 횟수 변경에 안전합니다.
배포기는 launchctl을 subprocess로만 부르고, 배포기 시험 모듈은 subprocess로 launchctl을 실행하려 하면
시험을 실패시키는 대역을 모듈 전체에 씌웁니다. 시험이 대역을 빠뜨리거나 회귀로 설치 되돌리기·서비스
재시작 경로에 들어가도 시험을 돌린 맥의 실제 서비스를 내리거나 재시작하지 않습니다. 설치 시험은 늘 임시
홈의 plist만 읽고 씁니다. 이 보장은 현재 배포기의 목록 형태 직접 실행 경로에 한정됩니다.
이 대역은 subprocess를 거치지 않는 실행(`os.system` 등), `shell=True`의 명령 문자열,
`env`나 래퍼 프로그램을 통한 간접 실행은 막지 않습니다. 범용 실행 샌드박스가 아닙니다.

정규 회귀 시험은 SMB 환경변수 각각/모두 누락 시 무출력 CONFIG 실패와 후속 I/O 미실행,
사전검사 정상 종료 및 중단 예외 전파도 확인합니다(배포기의 명령 실행은 대역으로 바꿉니다).
SSH 진입점은 임시 로컬 설치에서 실행 파일 누락/권한 오류/자식 실패를 그대로 실패로 전달하고
기본 설치로 우회하지 않는지 검증합니다. 각 설치가 남기는 표식 파일로 어느 설치가 실행됐는지 보므로,
출력을 버리고 기본 설치를 돌리거나 권한 없는 파일을 셸로 실행하는 회귀도 잡습니다.
표식은 실행마다 받은 인자 수를 한 줄씩 남기므로 같은 설치를 두 번 돌리거나 요청 문자열을 인자로 넘기는
회귀도 드러납니다. 표식은 진입점의 프로세스 그룹이 모두 끝난 뒤에 확인하므로, 진입점이 끝난 뒤 뒤에서
기본 설치를 띄우는 회귀도 잡습니다. setsid 등으로 그룹을 떠난 프로세스는 기다리지 못합니다.
그룹 대기의 EPERM 처리는 같은 사용자로 실행하는 macOS 시험에서 좀비만 남은 경우를 전제로 합니다.
다른 권한의 살아 있는 프로세스까지 종료되었다고 보증하지 않습니다. 리더 회수 뒤 그룹 번호가
재사용되면 무관한 그룹을 기다려 시간 초과가 날 가능성도 있어 범용 프로세스 감독기로 사용하지 않습니다.
이 로컬 시험은 sshd의 authorized_keys 해석이나 네트워크 단절 검증을 대신하지 않습니다.

### 격리 SSH 통합 시험

`SSHDiagnosticsTests`는 `setUpClass`의 서버 조기 종료와 기동 시간 초과 경로도 직접 호출합니다.
프로세스/소켓/시계는 mock으로 대체하고 임시 파일은 실제로 생성하여 메시지 접두, 로그 첨부,
class cleanup의 로그 닫기/임시 디렉터리 삭제 및 실행 중 서버 종료 요청을 검사합니다.
가짜 시계는 연결 실패 사건에서만 10초 경계로 이동합니다. 반복 조회는 시간을 진행시키지 않으며,
서버 상태 확인과 연결 실패 처리에 추가 조회를 삽입한 회귀 시험으로 호출 횟수 의존을 방지합니다.
이 검사는 실제 sshd 장애를 유발하는 E2E가 아니며 실제 연결 검증은 아래 opt-in 통합 시험이 담당합니다.

기동 실패/시간 초과, 단언 실패, SSH 클라이언트 실행 오류에는 임시 sshd 로그의 마지막 4KiB를
진단으로 첨부합니다. 로그가 없거나 읽을 수 없어도 원래 실패는 유지하며 성공한 시험에는 출력하지
않습니다. 이 로그는 시험용 서버의 진단으로 사용자명/임시 경로가 포함될 수 있으므로 공개 댓글에
그대로 복사하지 않습니다. 운영 SSH 로그나 키 파일은 읽지 않습니다. 포트 바인딩 충돌 자동 재시도와
Linux 환경 검증은 아직 포함하지 않습니다.

공개 저장소의 Actions 실패 로그에도 이 진단이 노출될 수 있습니다. CI는 운영 계정/키가 없는
GitHub-hosted 장비에서만 실행하고, 로컬 실패 로그를 공유하기 전에는 사용자명과 경로를 검토합니다.
서버 로그는 클래스 전체에서 공유하므로 이전 시험 기록이 섞일 수 있으며 해당 요청만의 로그가 아닙니다.
단언 진단은 unittest의 비공개 `_formatMessage` 훅에 의존하므로 Python 지원 버전을 확대할 때
`SSHDiagnosticsTests`로 첨부 여부를 재검증합니다. `add_note`는 프로젝트 최소 버전인 Python 3.11
이상에서 사용하며 3.10 이하 호환 분기는 제공하지 않습니다.
`SSHDiagnosticsTests`는 열 수 없는 로그(디렉터리)의 표시, 로그를 4KiB보다 많이 읽지 않는지, unittest의
기본 실패 문구를 지우지 않는지, msg 없는 단언과 클라이언트 오류 노트에 이 시험의 로그 끝부분이 붙는지,
성공한 통합 시험 본문이 로그를 읽지 않는지도 확인합니다.

`tests/test_ssh_integration.py`는 별도의 임시 sshd를 loopback의 임의 포트에 띄워 실제 SSH 연결로
`restrict,command=`를 검사합니다. 임시 호스트 키와 접속 키만 사용하고 사용자/시스템 SSH 설정,
authorized_keys, known_hosts는 사용하거나 변경하지 않습니다. 호스트키는 생성한 공개키로 고정하며
비밀번호 인증과 에이전트를 사용하지 않습니다. 실행되는 sync.sh도 종료 코드 23을 반환하는 임시 파일입니다.
클라이언트 표준 입력은 DEVNULL로 닫고 원격 강제 명령의 HOME도 임시 디렉터리로 한정합니다.
명령 인자가 없는 셸 요청도 별도로 거부를 검증합니다. PTY 거부 후 즉시 종료하는 경우에는 빈 출력,
PTY 없이 명령을 계속하는 경우에는 fixture의 출력과 종료 코드 23을 함께 확인합니다.

```sh
IMAGE_TEST_SSH=1 .venv/bin/python -m unittest discover -s tests -p test_ssh_integration.py -v
```

일반 사용자로 실행하며 sudo는 사용하지 않습니다. `ssh`, `ssh-keygen`, `sshd`가 필요합니다.
기본 로컬 전체 시험에서는 opt-in 없이는 건너뛰지만 CI는 `IMAGE_TEST_SSH=1`로 필수 실행합니다.
활성화 후 도구 누락/sshd 기동/인증 실패는 skip이 아니라 실패입니다. 시험 종료 시 서버와 임시 키를
정리합니다. 이 시험에서 포트 포워딩과 PTY는 서버 설정상 허용하므로, 거부되는 것은 키의 restrict
제한임을 확인합니다. SFTP도 서버에 설정한 뒤 강제 명령이 거절하는지 검증합니다.

검증 범위: 허용 명령과 종료 코드 보존, 임의 명령/SFTP 거부, 미등록 키 인증 거절, 직접/원격 포워딩
및 PTY 거부. 이 결과는 실제 운영 계정의 키 설정이나 두 runner의 네트워크/취소 동작을 보증하지 않습니다.

실제 SSH 취소 E2E는 아직 미실행입니다. 활성화 전에 운영과 분리된 시험 계정/서비스에서 두 runner 각각:

1. 올바른 고정 명령은 실행되고 `id`, 빈 명령, 추가 셸 명령, SFTP와 포워딩은 거부되는지 확인합니다.
2. 준비/전환/health 확인 단계 각각에서 SSH 단절 또는 job 취소를 발생시킵니다.
3. Actions 종료 상태만 믿지 말고 원격 프로세스와 잠금, `pending.json`, current SHA 및 health를 확인합니다.
4. 원격 작업이 계속되면 끝날 때까지 기다립니다. 종료되고 journal이 남으면 다음 sync의 복구를 확인합니다.
5. 복구 실패 시 journal을 삭제하거나 retry로 우회하지 않습니다. 원인 해결 후 정상 복구를 먼저 확인합니다.

SIGTERM은 예외 기반 정리 경로를 거치지만 SIGKILL/SIGHUP 등 즉시 종료는 다음 sync의 journal 복구에
의존합니다. SSH가 끊겨도 원격 작업이 계속될 수 있습니다. job 취소를 안전한 원격 종료의 대체로 쓰지 마세요.
운영 SSH 키/서비스 변경 및 해당 E2E는 별도 승인된 유지보수 작업입니다.
